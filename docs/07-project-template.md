# 07 — Super505 Project Template

The multi-instrument `.rpp` template (the item doc 06 §8 listed as "not yet done").

- **Repo copy:** `reaper/projects/super505-template.RPP`
- **Installed as:** `~/.config/REAPER/ProjectTemplates/Super505.RPP`
  → New Project from template → **Super505**.

Built for **this machine** (UR22C as Reaper's ALSA device `hw:UR22C`,
MT-PowerDrumKit.vst3 installed). Generated by
`scratchpad/build_template.py`-style assembly from real REAPER-authored chunks.

## Track layout

| # | Track | Source | → Super505 channel / loop column |
|---|-------|--------|----------------------------------|
| 1 | **Drum** | MT-PowerDrumKit VSTi (MIDI in) | ch1 → **column 1** (stereo kit summed to mono) |
| 2 | **Guitar 1** | UR22C **input 2** | ch2 → **column 2** |
| 3 | **Guitar 2** | UR22C **input 2** | ch3 → **column 3** |
| 4 | **Vocal** | UR22C **input 1** | ch4 → **column 4** |
| 5 | **Guitar 3** (spare) | UR22C **input 2** | ch5 → **column 5** |
| 6 | **Super505 Looper** | (bus) | `super505` → `super505_mixdown` → master |

The looper bus is **NCHAN 8**, record-armed + monitoring ON (so the JSFX runs and
emits LEDs — doc 06 §5 gotcha), record input = **all MIDI** (so Launchpad pads
reach it and **no hardware audio leaks** into the loop channels). `super505` slider
**Sync = project** (tempo-locked length, record-order-independent per doc 06 §7).

## Routing rationale

- Each instrument **sends** (post-fader, mono) into one looper channel via `AUXRECV`
  on the bus (`dstchan = 1024 + (column-1)`). Loops play back through
  `super505_mixdown` (folds ch1–8 → stereo 1/2) → master.
- **Live monitoring** is via the source tracks' master send, **not** the looper
  (looper channel monitor stays off by default), so live ≠ doubled (doc 06 §4).
- **Guitar 2 & Guitar 3 have `MAINSEND` off.** All three guitars share UR22C input
  2; if all sent to master you'd hear the live guitar 3× (+9 dB). Guitar 1 carries
  the live monitor; 2 & 3 still feed their loop columns. Move your live monitor by
  toggling which guitar track's master send is on.

## Manual steps after opening (not bakeable into the template)

1. **Launchpad MIDI** — confirmed on this machine: Launchpad Pro MK3 at
   `hw:5,0,0` / ALSA seq `36:0`, port **"LPProMK3 MIDI"** (Reaper device list
   `reaper-midihw-alsa.ini` index 3 = `hw:MK3`). Reaper already holds the **input**
   open (verified: `amidi` reports the raw port busy while Reaper runs → ALSA MIDI
   backend, input enabled).
   - **Enable the output:** Prefs → MIDI Devices → right-click **LPProMK3 MIDI** →
     *Enable output*. (Input is already on.)
   - On the **Super505 Looper** track, click the routing/IO (or FX-less "MIDI HW
     output") and set **MIDI hardware output → `LPProMK3 MIDI`** (template ships
     `MIDIOUT -1`; the encoded index is backend-specific, so it's left for the GUI
     — the LEDs lighting up is the confirmation). After setting it once, **save the
     project** and the `MIDIOUT` value can be baked back into the template.
2. **⚠️ Remove the DrivenByMoss control surface — REQUIRED on this machine.**
   This machine has DrivenByMoss installed (`reaper_drivenbymoss.so`; `reaper.ini`
   had `csurf_1=DrivenByMoss4Reaper`). DBM auto-claims the Launchpad Pro MK3 as a
   control surface and **silently consumes every pad press** before it reaches the
   track — so super505 gets no MIDI even though the notes arrive at Reaper. This was
   the real cause of "pads do nothing" / "pressing a pad selects the wrong track and
   plays" (the latter was DBM's own session-mode mapping, not super505).
   Fix: **Prefs → Control/OSC/web → select `DrivenByMoss4Reaper` → Remove** (fully
   reversible via Add). This is doc 05 Decision 1 — *not* moot here (it was only moot
   on the `bmini` dev machine, which had DBM uninstalled).
   - If the Launchpad gets stuck in Programmer mode after closing Reaper, reset with
     `tools/lp_programmer.sh live` (needs the port free — close Reaper first).
2. **Vocal = Yeti?** The template points Vocal at **UR22C input 1** because Reaper's
   audio device is `hw:UR22C` (ALSA), which can't see the separate Yeti USB card. To
   actually use the Yeti, either plug a mic into UR22C input 1, or switch Reaper's
   audio backend to **PipeWire/JACK** and reassign the Vocal track's input.
3. **Loop-length workflow** (doc 06 §7): set the master grid (top bar `length`) to
   your longest part (e.g. 8 bars), then per channel set `div` (drum `div=8` → 1-bar
   loop, chords `div=1` → 8-bar). Count-in is the `count-in: N` button.

## Audio device default (UR22C, not Yeti)

Reaper runs on the **JACK backend** (via pipewire-jack; `qjackctl` is PipeWire's
JACK graph — there is no real `jackd`). The Yeti was PipeWire's default sink+source,
so Reaper auto-connected there every start, needing a manual qjackctl re-patch.

**Desired policy:** Reaper forced to the **UR22C for both in and out**; *other*
apps default to **Yeti input / UR22C output**.

Setup (all persists across reboots):
1. UR22C card → **Pro Audio** profile (clean multichannel JACK ports, not the
   HiFi split-mono nodes):
   `pactl set-card-profile alsa_card.usb-Yamaha_Corporation_Steinberg_UR22C-00 pro-audio`
   → persists in `~/.local/state/wireplumber/default-profile` (`...UR22C-00=pro-audio`).
2. System defaults: **sink = UR22C**, **source = Yeti**
   (`wpctl set-default <UR22C-Pro-sink-id>` and `wpctl set-default <Yeti-source-id>`;
   ids from `wpctl status`) → persists in
   `~/.local/state/wireplumber/default-nodes`. This gives every app UR22C output and
   Yeti input. Reaper's *output* follows the default sink (UR22C) automatically.
3. **Reaper input override** — Reaper (JACK) auto-connects `REAPER:in1/in2` to the
   default source (Yeti). A systemd **user service** re-pins it to the UR22C:
   - script: `tools/reaper_ur22c_pin.sh` (a `pw-link` reconciler; same pattern as
     `route_guitar.sh`). Links UR22C `capture_AUX0/1` → `REAPER:in1/in2`, pins
     `REAPER:out1/2` → UR22C `playback_AUX0/1`, and drops any Yeti→Reaper input links.
   - service: `~/.config/systemd/user/reaper-ur22c-pin.service` (runs
     `reaper_ur22c_pin.sh watch`, enabled `WantedBy=default.target` → starts on boot).
   - manage: `systemctl --user {status,restart,disable} reaper-ur22c-pin.service`.

`capture_AUX0` = UR22C input 1, `capture_AUX1` = UR22C input 2 (matches the template
input map). A Reaper already running keeps old connections until the reconciler's next
pass (≤1 s) or a Reaper restart.

## Verification status

**Looper confirmed working end-to-end on this machine** (2026-06-27): Launchpad pads
drive super505 record/play after removing the DrivenByMoss surface; GUI controls work;
audio path verified. Pad→note mapping verified exact with `tools/lp_map.sh` (Record
81–85, Stop 71–75, Clear 61–65, all channel 1, MIDI port `36:0`).

Debugging tools added this session:
- `tools/lp_map.sh` — interactive pad→MIDI mapper (ALSA seq; works while Reaper runs).
- `tools/lp_programmer.sh` — Launchpad programmer-mode / paint helper (raw ALSA; needs
  the port free, i.e. Reaper closed).

Known good signal chain (verified): pad → `36:0` → PipeWire **Midi-Bridge** →
`REAPER:MIDI Input 4` → looper track (armed + **Monitor: Normal**) → super505. The
indirect Launchpad→Reaper path *through* the Midi-Bridge node (visible in qjackctl) is
normal for PipeWire — not a fault. super505 only reads MIDI while the track is
processing, so **Monitor must be Normal** (the JSFX GUI works regardless, so a working
GUI does not prove the input path).
